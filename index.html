Homework Part I: send requests to your API

1 · Install Postman

Mac
  1. Check your chip: Apple menu → About This Mac. It says Apple (M1, M2…) or Intel.
  2. Go to postman.com/downloads and download the Mac version for your chip.
  3. Open the .zip in Downloads. Drag Postman into Applications.
  4. Open it (⌘ Space → "Postman"). If the Mac warns it came from the internet, click Open.
  5. Have Homebrew? This does steps 2–3 for you: 
    brew install --cask postman
Windows with Ubuntu (WSL)
  1. Install Postman on Windows, not inside Ubuntu. It's a desktop app. It still reaches Supabase and your npm run dev app on localhost.
  2. Go to postman.com/downloads and download Windows. Run the .exe: it installs and opens by itself.
  3. Or paste this in PowerShell (not the Ubuntu terminal): 
    winget install --id Postman.Postman -e
  4. Find it later: Start menu → Postman.

Then, everyone: sign in or make a free account when Postman opens. Can't install it? Use web.postman.co, and if it asks how to send requests, choose the Cloud Agent.

2 · Find your API's address and key

  1. In your Supabase project: Integrations → Data API. Copy the Project URL. It ends in /rest/v1/: keep /rest/v1, delete only the last /. That's your base_url: https://your-project-id.supabase.co/rest/v1. The Docs link there explains every endpoint for your tables.
  2. Project Settings → API Keys: copy the Publishable key. Never use the secret key in Postman or in front-end code.

3 · Let the publishable key in (temporary)

  1. Send GET {{base_url}}/<a table>. If you get [] but the Table Editor has rows, Row Level Security is on with no rules.
  2. In your supabase folder, start claude and paste this (change the table names to yours): 
    My tables have Row Level Security on with no policies, so my publishable key gets [] back in Postman and can't add rows. We don't have logins yet.

Using the Supabase MCP, add TEMPORARY development policies that let the anon role read and write all my tables (LIST YOUR TABLES). Name each one "dev: open access until auth". Show me the SQL first and wait for my approval.
  3. Read the SQL before you approve. These rules are for development only; real per-user rules come with logins in a future lecture.

4 · Send every CRUD request in Postman

  1. New collection → Variables: base_url and publishable_key. Click Save.
  2. New request → Headers → Bulk Edit → paste, then Duplicate this request for every new one: 
    apikey:{{publishable_key}}
Authorization:Bearer {{publishable_key}}
Content-Type:application/json
  3. For each table: POST a row (add the header Prefer:return=representation to get the new row back), GET all rows, GET with a filter (?column=eq.value), PATCH one row (?id=eq.<id>), DELETE one row. Always filter a PATCH and a DELETE.
  4. After each one, note the status code, the response body, and what changed in the Table Editor.
  5. If your tables have a user_id, keep one user row: your app uses it in Part II, until we add logins.

5 · Write your notes for Claude

  1. Make supabase/api_notes.md: one example request per table that worked, plus anything tricky (required columns, foreign keys, filters your app needs, errors you hit).
  2. This is context for Claude in Part II. If you can explain your API, you can check Claude's work.

Homework Part II: make it full-stack

6 · One project folder

  1. Commit first (git add -A && git commit -m "Before full-stack"), so you can undo anything.
  2. In your project's root (the folder that has supabase/ inside it), start claude and paste: 
    Restructure this project into the full-stack layout below. Move files only: don't change any code.

my-app/
├── .claude/      skills/ and agents/ from BOTH ./.claude and ./supabase/.claude, merged
├── .mcp.json     moved up from supabase/
├── front-end/    everything that belongs to the React app (src, public, app_outline, index.html, package files, vite and lint config, .gitignore, node_modules)
├── supabase/     my database files (schema.sql, user_stories.md, ERD screenshot, api_notes.md)
├── CLAUDE.md     update it to describe both halves
└── README.md

Show me the plan (what moves where) first and wait for my approval.
  3. Exit Claude, start it again in the root, choose Use this MCP server. Check /mcp (supabase connected) and /agents (front-end-agent and supabase-agent).
No supabase-agent in /agents? 
mkdir -p .claude/agents && curl -fsSL https://raw.githubusercontent.com/kabeier/Databases-and-Supabase/main/demo-kit/.claude/agents/supabase-agent.md -o .claude/agents/supabase-agent.md

7 · Keep the key secret

  1. Make front-end/.env (next to package.json) with your values, no quotes. The URL here has no /rest/v1 (the code adds it): 
    VITE_SUPABASE_URL=https://your-project-id.supabase.co
VITE_SUPABASE_ANON_KEY=your-publishable-key
  2. Add a line with .env to the .gitignore in your project root (make the file if it isn't there). Run git status: .env must not be listed.

8 · Hand it to Claude, then review the plan

  1. In Claude (project root), type /model and pick Opus. Paste the prompt: 
    My current front-end application is working as desired and I want to preserve the existing UI and user experience along with my supabase projects database structure. Now I would like to integrate these two projects as one (expose API endpoints and connect UI actions within the React app to the Supabase project) to create a full stack application.

I want you to use the subagents of front-end-agent and supabase-agent to communicate with one another to accomplish this task while using you as their main orchestrator for this task.

Do not change any fundamental functionality and/or data without my approval.

**DO NOT IMPLEMENT AUTHENTICATION NOR AUTHORIZATION PRINCIPLES**

Once the Sub-Agents return a completed action use both the Playwright MCP and the Supabase MCP to walk through the applications features yourself and test them out to ensure a successful integration.
  2. Read the plan before you approve: one service file for all Supabase requests, keys from import.meta.env, no new tables, no login, no RLS changes. You can point Claude at @supabase/api_notes.md.
  3. Asked about user_id? "Use the one user in my users table for every new row. No login yet." Asked about the old fake data? "Remove it. The database is the source of truth."

9 · Prove it, then commit

  1. cd front-end && npm run dev. Add something. Refresh. Still there? Find the row in the Table Editor.
  2. Add a row in the Table Editor, refresh your app: it should show up.
  3. Read Claude's summary, especially its assumptions. Then git status (no .env!), commit and push.
  1. All the promptsDev rules, restructure, connect, and good answers to Claude's questions.
  2. supabaseApi.jsTicked's service layer: the same requests as Postman, in code.
  3. db.jsTicked's data functions, now calling the API instead of arrays.
  4. dev-policies.sqlThe temporary RLS rules, as SQL.
